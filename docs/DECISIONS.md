# Decisions

Non-obvious choices and their trade-offs, dated, newest section first. Read the relevant entry before changing a mechanism that looks odd. Choices made autonomously under a delegation are recorded here for the user to review; an entry is a record, not a claim that the capability is complete.

## 2026-10-15

| Decision | Reason and trade-off |
| --- | --- |
| The type checker is mypy in strict mode, run by `scripts/typecheck.sh` over `chatctl/` and `tests/` as a gate in `scripts/check.sh`, with its configuration pinned under `[tool.mypy]` in `pyproject.toml`. basedpyright was tried and not adopted. | On this code both found the same single real error (an `Optional` that the exactly-one check in `cutoff_from` guarantees but no checker can follow), both handle the PEP 695 generic in `cli.py`, and both run in well under a second. basedpyright's strict mode reported 75 errors to mypy's 43, almost all unannotated pytest parameters and their knock-on "unknown type" reports, and its default mode adds over a hundred warnings about argparse's `Namespace` being `Any` and unused `add_argument` results. It also installs a bundled Node.js, roughly 280 MB in every worktree's `.venv` against roughly 70 MB for mypy with its compiled extension and dependencies. The cost is pyright's stricter inference of unknown types, which this code, with no third-party dependencies, gains little from. |
| Test functions in `tests/` are exempt from mypy's annotation requirement (`disallow_untyped_defs` and `disallow_incomplete_defs` are off for `tests.*`); their bodies are still checked, and shared test helpers are annotated. | pytest injects fixtures and parametrized values by name, so annotating every test signature adds ceremony without catching bugs. The trade-off is that a parametrized value is `Any` inside its test, so a call that passes it to annotated code is not checked. Annotate a test where that matters; drop the override if the tests are ever annotated throughout. |
| Selection also skips a conversation whose `conversation_template_id` is present and non-null, with its own reason (`conversation-template-id-set`). A missing `conversation_template_id` is not a reason to skip. | [api-findings.md](api-findings.md), question 5, records `conversation_template_id` as non-null on as many items as `gizmo_id` without recording whether they are the same items, and [AGENTS.md](../AGENTS.md#rules) says any doubt about membership means skip. If they are the same items the check never fires, since `gizmo_id` is checked first; if not, it holds back conversations whose kind is unknown. A distinct reason keeps those countable in a dry run. Only `gizmo_id` is required to be present, because that is the recorded membership field; requiring this one too would turn a harmless API change into archiving nothing. Revisit once the probe records whether the two fields coincide. |
| Selection accepts a conversation id only if it is made of ASCII letters, digits, `-` and `_`, and skips any other as `bad-id`. The UUID-like format is not required. | Ids go into the `PATCH /backend-api/conversation/<id>` path and the manifest, so a value with `/`, `.`, `?`, `#`, `%`, whitespace or control characters could address a different resource or corrupt the manifest. Refusing them is simpler and safer than escaping them. The id format is not recorded in api-findings, so nothing stricter is assumed. |

## 2026-10-14

| Decision | Reason and trade-off |
| --- | --- |
| chatctl archives only conversations whose `gizmo_id` is present and null, so it skips project conversations (`g-p-` prefix), custom GPT conversations (other `g-` prefixes) and any item without the field. The rule is in [AGENTS.md](../AGENTS.md#rules). | The listing mixes all three kinds and marks them only by `gizmo_id` ([api-findings.md](api-findings.md), questions 5 and 6). A null check does not depend on the undocumented prefix scheme, so a new or unrecognised prefix is skipped rather than archived, and requiring the field to be present means an API change that drops it stops archiving rather than archiving everything. The cost is that custom GPT conversations cannot be bulk-archived; an opt-in for them would need its own finding and decision. |
| Git hooks are plain scripts in a tracked `.githooks/` directory, enabled by `git config core.hooksPath .githooks` in `scripts/setup.sh`. | No extra tool to install, locally or in CI. Lefthook or the `pre-commit` framework would add staged-file stashing and parallelism, which a repository this size does not need. Revisit if the hooks grow past a few checks. |
| The pre-commit hook only checks; it never rewrites files. It runs ruff against the staged blob of each staged Python file (`git show :path`), so unstaged edits neither hide nor cause failures. | A rewriting hook would need to restage files and could mix unstaged changes into the commit. `bash scripts/format.sh` is the explicit fix-up. |
| No type checker gate yet; `scripts/check.sh` runs fmt-check, lint and test only. Superseded on 2026-10-15 by the mypy gate. | The code is annotated but has never been checked, and choosing between mypy and basedpyright (and how strict) is its own change. Queued in `TODO.md` as `choose-type-checker`. |
| `scripts/test.sh` fails when `node --test` collects no tests. | `node --test` exits 0 with zero tests, which would let a renamed or moved test file pass silently. pytest already exits 5 on empty collection. |
| Scheduled validation of main is deferred; there is no `main-validation.yml`. | Every check is fast enough to run on each PR and push, so a scheduled run would repeat PR CI. Add it when there is an expensive suite, or when the review ledger is in regular use and `review-due.sh` is worth scheduling. |
| Node is pinned in `.nvmrc` (major 26) for the probe's tests. | CI reads the pin from a file instead of a version typed into the workflow. The probe itself runs in whatever browser the user has; Node only runs its tests. |
| Design specs moved from `docs/superpowers/specs/` to `docs/specs/`; new plans go in `plans/`. The completed repo-skeleton plan was deleted rather than moved. | Docket's layout names directories after their content, not the tool that wrote them. Everything the plan described merged in #1 and git history keeps the plan. It quoted whole files, and docket's `check-links.sh` reads link syntax inside fenced code, so the quoted relative links failed the link check from their new location. |
| `main` is protected by the "Protect main" ruleset, configured by the user: required checks `check` and `Queue and PR hygiene`, PR required with squash only and zero approvals, no force pushes or deletion, admin bypass. Up-to-date-with-base is off. | Requiring branches to be up to date would mean a rebase and CI rerun before every merge; with one person merging, the push run on `main` and the red-main policy catch the rare broken combination more cheaply. The admin bypass is what lets queue, plan and spec commits go straight to `main`. Approvals stay at zero because the reviewers are agents the forge cannot see; the review comment is the record. |
